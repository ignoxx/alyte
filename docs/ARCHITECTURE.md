# Alyte architecture

## Status

This is the implementation architecture for the first public iOS release. Product behavior belongs
in `MVP.md`; canonical terms belong in `CONTEXT.md`; durable trade-offs belong in `docs/adr/`.

## Architecture goals

The system is optimized for five things, in this order:

1. a complete account-free laboratory-history product;
2. truthful separation of measured, user-entered, estimated, and evidence-backed data;
3. minimum practical exposure of health content to cloud infrastructure;
4. fast capture and resilient asynchronous processing; and
5. a small codebase a solo developer and coding agents can change safely before the Shipaton
   deadline.

The local iPhone database is the source of truth. The backend sells and performs optional
processing; it is not the health-record system.

## System shape

```text
                           optional, paid boundary
┌──────────────────────── iPhone ────────────────────────┐
│ React Native screens                                  │
│        │                                               │
│ typed feature services + pure domain functions        │
│        │                         │                     │
│ SQLite repositories        native iOS adapters        │
│        │                    Vision / PDFKit / CryptoKit│
│ protected files + DB             │                    │
│        └──────────── local source of truth ────────────│
└───────────────────────┬────────────────────────────────┘
                        │ explicit consent, minimum payload
                        ▼
┌──────────────────── Cloud API ─────────────────────────┐
│ Apple identity + RevenueCat entitlement verification  │
│ request admission + idempotency + usage ledger        │
│ temporary upload ──► worker ──► model adapter          │
│                         │                              │
│ strict validation + evidence resolution               │
│                         │                              │
│ device-encrypted result cache, maximum 24 hours        │
└────────────────────────────────────────────────────────┘
```

The backend stores account, purchase, allowance, and opaque request metadata. It does not store Lab
Reports, Measurements, Intake Events, or readable completed analyses as durable user records.

## Repository layout

Start as a small npm workspace:

```text
apps/
  mobile/                 Expo/React Native application
  api/                    HTTP admission API and background worker entrypoints
packages/
  contracts/              versioned cloud request/response schemas
  domain/                 pure IDs, value objects, normalization, trend and insight logic
  catalogue/              biomarker, unit, guidance, evidence, and alias source data
  fixtures/               synthetic multilingual reports and intake images
docs/
  adr/                    durable decisions
```

`packages/domain`, `packages/contracts`, and generated catalogue artifacts must remain independent
of React, Expo, Node-only APIs, and provider SDKs. Mobile and backend adapters depend inward on
those packages.

Local development runs directly on the host with `npm run dev`; that command watches the mobile,
API, and shared-package sources and restarts or reloads the affected process. Docker is not required
for ordinary development. The production service may use a container generated by Railway's build
system, but local and CI correctness cannot depend on a Docker daemon.

## Mobile stack

The scaffold should use the current stable Expo SDK at implementation time; the inspected T3 Code
baseline used Expo 56, React Native 0.85, React 19, and TypeScript. Pin exact versions in the lockfile
instead of copying them from this document later.

Use:

- React Native with Expo and TypeScript strict mode;
- an Expo development client rather than Expo Go;
- React Navigation native stack and bottom tabs;
- Expo Camera, Document Picker, Image Picker, File System, Secure Store, SQLite, Sharing, and
  Local Authentication where their contracts are sufficient;
- local Expo modules written in Swift for Vision, PDFKit, file protection, and CryptoKit;
- a token-based theme and a small primitive layer such as `AppText`, `AppButton`, `AppSurface`,
  `StatusPill`, and `EmptyState`;
- development, preview, and production variants with separate bundle identifiers; and
- EAS Build. If EAS Update is enabled, use the native fingerprint runtime policy so JavaScript is
  never delivered to an incompatible native binary.

Ordinary interface work stays in React Native. Swift owns capabilities whose correctness or privacy
depends on Apple frameworks. Generated `ios/` and future `android/` directories remain reproducible
from tracked Expo modules and config plugins.

### Navigation

The accepted account-free laboratory structure is:

```text
Root stack
├── onboarding
├── main tabs
│   ├── Home stack
│   ├── Labs stack
│   └── Settings stack
├── full-screen report-import task
│   ├── source selection / password
│   ├── privacy and redaction workspace
│   ├── extraction progress
│   ├── compact draft review
│   └── completion
└── full-screen and form-sheet support flows
    ├── measurement correction and source preview
    ├── export, deletion, protection, and support
    └── later cloud consent, paywall, and intake correction
```

Use UIKit-owned native tabs, stacks, headers, full-screen modals, menus, and sheets. The report
import task sits above the tabs so the tab bar cannot cover document or confirmation controls.
Snap and Log remain dormant feature code until the later cloud/intake slice has useful analysis and
an accepted navigation design; local sign-in state must not unexpectedly rearrange peer tabs.

### Native modules

Build narrow, typed modules rather than one general native bridge.

`AlyteVision`:

- accepts protected local image paths and orientation metadata;
- uses iOS 26 Vision document recognition over rendered Sanitized Report pages;
- returns document regions, tables, rows, cells, text, normalized bounding boxes, candidate
  alternatives, and internal recognition confidence;
- supports explicit recognition-language hints while allowing automatic detection; and
- never logs recognized content.

`AlyteLocalModels`:

- owns optional on-device semantic model-pack discovery, download state, integrity verification,
  activation, load/unload, inference cancellation, and deletion behind one typed Expo module;
- consumes a versioned Alyte manifest containing the Hugging Face repository, immutable commit,
  exact allowlisted filenames, publisher, license, runtime/quantization, byte size, SHA-256,
  supported languages, prompt/schema compatibility, and device requirements;
- downloads public, ungated files directly from Hugging Face over HTTPS when possible, follows the
  resolved CDN response, resumes safely when supported, and restarts cleanly otherwise;
- rejects moving revisions, unlisted files, checksum mismatches, unsupported licenses/runtimes, and
  gated repositories that would require a user or bundled access token;
- stores completed packs under Application Support, excludes them from iCloud Backup, stages
  partial downloads separately, and atomically promotes a verified pack;
- loads at most one pack at a time, releases it under memory or thermal pressure, and exposes
  observable not-installed, downloading, verifying, ready, loaded, failed, and deleting states;
- permits multiple selectable packs only in development/evaluation builds while release builds
  expose one recommended pack and user-visible storage/delete controls; and
- never logs structured OCR input, prompts, generated tokens, or model results.

`AlytePDF`:

- inspects page count, dimensions, encryption state, metadata, and text-layer presence;
- unlocks a password-protected PDF for the current import session;
- exposes a native PDFKit viewer surface with aspect-correct page layout, zoom, pan, page navigation,
  and coordinate transforms for direct redaction editing;
- renders selected pages to images with stable transforms;
- applies crop and rotation transforms;
- burns redactions into newly rendered pages;
- creates a new sanitized PDF without the original text layer, annotations, attachments, or
  document metadata; and
- verifies the sanitized artifact has no selectable source text or removable redaction objects.

`AlyteProtection`:

- applies iOS Data Protection to the database, WAL/SHM siblings, reports, images, exports in
  progress, and derived artifacts;
- marks health-content paths as excluded from iCloud Backup; and
- reports protection failures instead of silently continuing.

`AlyteDeviceCrypto`:

- creates and retains the device result-decryption key in Keychain/CryptoKit;
- exposes only the public key to JavaScript;
- decrypts cloud-result envelopes locally; and
- provides a simulator/test fallback that never ships as a production default.

Database-level SQLCipher encryption is not a launch dependency. The first release uses iOS Data
Protection, backup exclusion, app-container isolation, optional biometric app lock, and Keychain
protection. A focused threat-model spike may add SQLCipher only if it does not put migrations,
performance, or Expo upgrades at risk.

## Local persistence

### Database rules

Use SQLite as the structured source of truth, with:

- explicit forward-only numbered migrations;
- `PRAGMA foreign_keys = ON`;
- WAL mode after confirming file-protection behavior for the database and its sidecars;
- parameterized statements only;
- transactions around imports, corrections, deletes, and cloud-result application;
- UUIDv7 or another sortable opaque identifier generated on-device; and
- ISO timestamps stored in UTC plus explicit source-local date fields where a laboratory date has
  no reliable time zone.

Use small typed repository modules over direct `expo-sqlite` calls. Decode database rows at the
boundary. Screens never contain SQL.

### Core tables

The first schema needs these record families. Exact column names may evolve, but their separation
must remain.

| Table | Purpose |
| --- | --- |
| `lab_reports` | Imported source metadata, local paths, import state, and source hash |
| `lab_report_pages` | Page order, dimensions, crop, rotation, redaction recipe, derived path |
| `lab_records` | One specimen-collection event, date state, specimen, laboratory metadata |
| `measurements` | Original and normalized result data plus row-level review state |
| `measurement_corrections` | Audit of extracted value to current user-confirmed value |
| `intake_events` | Time-stamped consumption record and Analysis Inclusion state |
| `intake_components` | User-entered or recognized substances and amount/dose state |
| `nutrition_estimates` | Internal ranges, provenance, estimate quality, and schema/model version |
| `cloud_jobs` | Durable device outbox and request/result lifecycle |
| `saved_insights` | Reproducible snapshot with source IDs and catalogue version |
| `insight_feedback` | Correction, dismissal, and relevance feedback from this device |
| `catalogue_state` | Installed signed catalogue version and verification metadata |
| `app_preferences` | Non-secret local preferences and onboarding state |

Catalogue definitions may ship as signed, read-only generated data rather than user tables. Never
join on translated display names; use canonical IDs.

### Measurement representation

Preserve source and normalized values separately:

- original label and locale;
- original value string, comparator, value type, unit string, interval text, and lab flag;
- parsed decimal value where applicable;
- canonical Biomarker ID only when the alias/specimen mapping is safe;
- normalized value and unit only when deterministic conversion is supported;
- source bounding box/page provenance;
- extracted, reviewed, corrected, or unresolved state; and
- internal reasons that require review.

The trend query includes only compatible exact numeric Measurements with a known collection date.
Missing tests create gaps in evidence, not zero values or interpolated points.

### Files

Use separate protected directories for originals, working pages, sanitized derivatives, intake
media, transient imports, and exports. Store paths and hashes in SQLite, not file bytes. A single
file service owns creation, protection, backup exclusion, reference counting, and deletion so
database and filesystem state cannot drift silently.

The Original Report is immutable. Crop, rotation, and redaction remain reversible editing recipes
until the person finishes the privacy workspace. The Sanitized Report is a newly rendered
derivative, never overwrites the original, and becomes the working document for extraction, exact
preview, export, and any later cloud upload.

## Local import pipeline

```text
Files/Photos selection
  → copy into protected app storage
  → inspect PDF / ask for password when required
  → full-screen privacy workspace and page transforms
  → render and verify Sanitized Report
  → Vision document/table recognition over sanitized pages
  → measurement-candidate filtering
  → optional schema-constrained local semantic mapping through the active verified model pack
  → locale-aware alias and unit mapper
  → deterministic semantic validation
  → compact editable Extraction Draft
  → exception-focused user review
  → atomic Lab Report + Lab Record + Measurement save
```

Recognition confidence is an internal routing signal. The user sees the precise field or row that
needs review and why; they do not see a medical-looking confidence percentage.

Parsing occurs in layers:

1. Vision returns immutable source observations with page geometry from the Sanitized Report;
2. Vision document structure and deterministic layout logic identify tables, rows, panels, and
   other measurement-shaped candidates;
3. locale parsers recognize dates, decimals, comparators, intervals, and units;
4. the multilingual alias catalogue proposes canonical Biomarker IDs;
5. where the device, input language, and installed pack are supported, an on-device model receives
   small structured OCR chunks and may select source cell IDs, classify section/row specimen, or
   propose semantic roles and canonical candidates through a versioned schema;
6. deterministic validators copy exact source values, reject invented cell IDs and incompatible
   specimen/value/unit mappings, and decide which fields genuinely need review; and
7. the user inspects a grouped table, resolves the exceptions, and confirms the draft.

Raw OCR or PDF text observations are retained only as internal provenance. They do not each become
a draft row. Unknown measurement-shaped results remain preserved even when they cannot be mapped;
unrelated headers, addresses, licences, and prose do not become user review work.

The semantic mapper remains provider- and model-neutral. Candidate model packs are benchmarked
against identical structured OCR fixtures before one is recommended for release; no model name is
part of the Extraction Draft contract. The iOS 26 Foundation Models framework may remain an
optional accelerator where available, but it is not the local contract and does not replace a
downloadable pack for unsupported languages. Chunk every semantic request by table and bounded row
count, accept only source identifiers that exist, reject duplicate source-row consumption, and
never let a model author authoritative numbers, units, ranges, conversions, translations, or
medical explanations. The catalogue owns localized display names while exact source labels remain
provenance.

Model weights are executable inputs even when they contain no health record. Alyte therefore
accepts only manifest-pinned inference formats from reviewed repositories and never loads pickle or
arbitrary code from the Hub. Download availability is an enhancement boundary: missing, deleted,
corrupt, incompatible, or interrupted packs fall back to Vision structure, locale parsing, aliases,
deterministic validation, and focused user review without blocking local mode.

Cloud report extraction is a fallback for selected, sanitized pages. It produces another editable
Extraction Draft and never bypasses review.

## Intake pipeline

This pipeline belongs to the cloud/intake implementation slice after the local laboratory gate. Its
code and persistence remain part of the architecture while its incomplete UI stays out of the
account-free laboratory phase.

Snap must complete its foreground work quickly:

```text
capture
  → protected local file + Intake Event in one user-visible action
  → return to the day view
  → local cloud job uploads when consent, entitlement, and network allow
  → backend recognition result
  → device decrypts, validates, and applies editable components
  → deterministic nutrition buckets and catalogue-backed relationships
```

If the app suspends before upload, the outbox resumes on foreground. If upload completed, backend
processing continues and the result is fetched on the next foreground. iOS background execution is
an optimization, not a correctness requirement.

The cloud recognizer may return up to five open-vocabulary Influence Candidates. It is not prompted
with only the 15 Comparable Biomarkers. Candidates become visible Potential Relationships only
after mapping to approved Evidence Relationships. Unmapped candidates may be summarized as
`No reviewed relationship available` without repeating an unsupported model claim.

Nutrition output stores broad ranges and provenance. A deterministic, versioned function converts
those ranges into qualitative Nutrition Buckets. User quantities and verified label facts outrank
photo estimates.

## State and domain logic

Do not copy T3 Code's event-sourced server or Effect graph into this smaller app.

Use:

- dependency-injected service interfaces for database, files, native OCR/PDF, catalogue, cloud,
  purchases, and time;
- React contexts only for process-wide service instances and session/preferences;
- feature hooks backed by repository queries and a small invalidation/change-feed layer;
- `useSyncExternalStore` or an equally small observable boundary for live queries; and
- pure functions for normalization, comparison, chart models, Nutrition Buckets, evidence
  resolution, and wording guards.

Persist durable workflow state such as imports and cloud jobs. Keep transient sheet, selection, and
camera state inside the owning screen or flow. Do not put PDFs, images, large OCR payloads, or entire
database query results in a global JavaScript store.

Feature folders should own their screens, hooks, view models, domain helpers, and focused tests:

```text
src/features/
  onboarding/
  home/
  labs/
  import/
  redaction/
  biomarkers/
  intake/
  insights/
  cloud/
  paywall/
  privacy/
  settings/
```

## Charts and insight derivation

Charts consume a pure chart model, not database rows. The model identifies measured points,
laboratory intervals, General Guidance, missing dates, unit incompatibilities, and selection state.
Only measured points receive a solid trend line. Possible relationships appear as separately
labeled contextual events or bands and never extend the measured curve.

Select the chart renderer during the first technical spike by testing VoiceOver access, Dynamic
Type labels, dark mode, and scrolling performance on an iPhone 15 Pro running iOS 26. The domain chart model must not
depend on that renderer, so the library can be replaced without changing health logic.

Related Wellness Context is derived locally from:

- at least two compatible Measurements;
- repeated included Intake Events within the relevant interval;
- approved Evidence Relationships whose time horizon and caveats fit; and
- the catalogue version used for the calculation.

Saved output records all source IDs. Editing, excluding, or deleting a source invalidates the old
insight and locally recomputes current context.

## Evidence catalogue

The catalogue source is reviewed data in the repository, compiled into deterministic artifacts for
mobile and backend use. Each entry has a stable ID, schema version, content version, sources,
review date, jurisdiction/applicability, and concise display copy.

The catalogue contains separate schemas for:

- Biomarker definitions, aliases, specimens, and compatible units;
- deterministic unit conversions;
- laboratory General Guidance;
- biomarker explanations; and
- intake-to-biomarker Evidence Relationships.

Build tooling validates references, IDs, units, direction values, required caveats, review dates,
and forbidden wording. A signed release artifact can update without an account. A catalogue update
never mutates source Measurements and does not rewrite the provenance of saved insights.

## Cloud architecture

### Services

Use Node.js 24 LTS, strict TypeScript, Fastify, `better-sqlite3`, and one production process with
three cooperating runtime responsibilities:

- the HTTP API for identity, admission, upload, request status, result retrieval, account export,
  and deletion;
- a bounded background job runner for provider calls, validation, result encryption, and retries;
  and
- a cleanup scheduler for expired uploads, leases, sessions, and encrypted result envelopes.

Deploy that process as one Railway service in EU West (Amsterdam) with one persistent volume. Keep
the SQLite database, its WAL/SHM companions, transient upload directory, and encrypted result
envelopes below the mounted runtime path. Railway configuration and the start command own runtime
migrations because the volume is not present during the image build or pre-deploy phase.

The first release intentionally has no Postgres, Redis, separate queue service, or object store.
The backend remains internally modular so database, queue, upload, and result-store adapters can be
replaced when real usage requires multiple machines or stronger availability. Do not increase the
Railway replica count while SQLite and the transient file store remain attached to one volume.

Production is the first hosted environment; no persistent staging environment is required before
the app is released. Tests, synthetic fixtures, local provider adapters, and StoreKit sandbox cover
pre-production verification. A separate staging environment can be added after production and real
users exist.

### Durable SQLite queue

`cloud_requests`, `analysis_jobs`, encrypted result metadata, account/session state, and the
append-only allowance ledger share the backend SQLite database. Queue rows contain only opaque
request/upload identifiers and non-sensitive operational metadata. Each row records state,
availability, attempts, lease owner/expiry, handler version, request/schema/prompt versions, and a
non-sensitive failure category.

The runner claims work in a short atomic transaction, performs provider work outside the
transaction, and heartbeats a time-limited lease. A crash or deployment leaves the row intact; a
later runner reclaims expired leases. Transient failures retry with bounded exponential backoff,
while permanent validation or safety failures become non-chargeable terminal states. Unique
constraints on request/result and allowance-ledger identifiers make completion and charging
idempotent.

Every deploy must support queued jobs created by the previous handler version. Introduce breaking
job changes by first deploying code that reads old and new versions, then enqueue the new version,
drain old jobs, and remove the old handler later. Database migrations run before the API reports
ready or the runner starts claiming work.

Railway sends the old process `SIGTERM`; the service stops admitting work and claiming jobs, drains
HTTP, lets in-flight jobs finish for the configured grace period, and closes SQLite. If a job cannot
finish, its lease expires for the new process. Volume-backed releases may have brief downtime, which
is accepted for the MVP. Configure a health endpoint, restart policy, and deployment draining time.

Temporary uploads live on the same persistent volume and are deleted immediately after provider use
plus by defensive expiry cleanup. Filesystem deletion cannot be atomic with SQLite, so completion
records cleanup intent and the scheduler removes any orphan. Scheduled volume backups and a tested
encrypted off-platform SQLite backup protect durable operational state; transient health uploads do
not need long-term backup retention.

### Durable backend data

Permitted durable fields include:

- internal account ID and Apple subject identifier;
- RevenueCat customer/entitlement identifiers and webhook event IDs;
- current allowance period and append-only usage transactions;
- request ID, operation, timestamps, byte/page counts, status, provider/model/schema versions,
  error category, and encrypted-result expiry; and
- audit events for account export and deletion without health payloads.

Do not place filenames, OCR text, Biomarkers, Measurements, medication names, recognized foods,
prompt bodies containing user data, or readable model responses in SQLite, analytics, traces,
or error reports.

### Request protocol

All mutating endpoints accept an idempotency key generated on-device.

1. `POST /v1/cloud-requests` validates identity, entitlement, allowance, operation limits, content
   metadata, and the device public key. It returns an opaque request ID and upload instructions.
2. The device uploads the minimum artifact. Report uploads use only selected sanitized page images,
   not the Original Report.
3. `POST /v1/cloud-requests/{id}/complete-upload` seals admission and atomically inserts a durable
   SQLite job.
4. The runner reads the artifact from transient volume storage, invokes the configured model adapter, validates the response,
   deletes the upload, and either records a non-chargeable failure or atomically consumes one unit
   when a usable schema-valid result exists.
5. The worker encrypts the result for the requesting device, removes plaintext process buffers as
   practical, and stores only the envelope in the TTL result store.
6. `GET /v1/cloud-requests/{id}` returns status and non-sensitive failure categories.
7. `GET /v1/cloud-requests/{id}/result` returns the encrypted envelope. Successful retrieval deletes
   it early; expiry deletes it automatically.

A completed result consumes allowance even when the device never retrieves it. Provider or schema
failure does not. Retries cannot double-charge because the ledger transaction is unique by request
ID and operation.

### Result encryption

The device registers a per-installation public key with each request. After validation, the worker
uses ephemeral authenticated key agreement to create an AEAD-encrypted result envelope. The
matching private key remains in Keychain/CryptoKit and decryption occurs in `AlyteDeviceCrypto`.

The exact P-256 ECDH, HKDF, and AES-GCM envelope format must be documented in `packages/contracts`
with cross-language test vectors. TLS still protects uploads and status calls; device encryption
limits readable result retention after processing, but it does not pretend the worker or selected
AI provider never saw the submitted content.

### Identity, purchases, and usage

- Local mode has no account.
- The first cloud action presents the disclosure, Sign in with Apple, and purchase flow.
- The backend verifies Apple identity tokens and issues a short-lived app session plus refresh token
  stored in Keychain.
- RevenueCat handles StoreKit products and webhooks; the backend remains authoritative for cloud
  allowance consumption.
- Starter Pack units persist on the account until used. Subscription units reset at the StoreKit
  billing-period boundary and do not roll over.
- Home does not show a permanent meter. The backend returns coarse warning state around 80%, 95%,
  and exhaustion.
- Account deletion revokes sessions and deletes account, purchase-linked app data where legally
  permitted, usage/request metadata, pending uploads, and cached results. It leaves local records
  untouched.

## Cloud model boundary

Provider SDKs live only behind backend adapters. The default launch model is selected through a
fixture evaluation rather than hard-coded into the product architecture.

Every operation has:

- a versioned prompt and response schema;
- explicit image resizing and detail settings;
- a maximum input size/page count;
- a timeout and bounded retry policy;
- syntactic and semantic validation;
- stored provider/model/schema metadata without prompt or health content;
- a private synthetic/de-identified evaluation set; and
- cost, latency, schema-validity, and useful-result metrics.

For Intake Images, separate observation from approved interpretation. The model may describe visible
items, read a label, estimate broad amounts, and propose Influence Candidates. User-facing health
copy is assembled from validated structured observations and catalogue entries, never free-form
model medical prose.

For Lab Reports, the model returns source-shaped fields and review reasons. Deterministic code owns
canonical IDs, decimal parsing, unit conversion, comparison compatibility, and General Guidance.

## Privacy, logging, and analytics

- Log opaque IDs, operation types, durations, byte counts, status codes, and error categories.
- Redact request bodies and headers at the framework boundary.
- Never attach user media or extracted health text to crash reports or support mail.
- Use Apple aggregate App Analytics and scrubbed MetricKit diagnostics by default.
- Any first-party product analytics are opt-in, coarse, and contain no health content.
- The support composer starts with a scrubbed diagnostic template and attaches nothing
  automatically.
- Secrets live in the hosting provider's secret manager and are rotated without an app release.

## Export and deletion

Full Export is generated locally from one consistent database transaction/snapshot. It includes a
versioned manifest, structured JSON, human-readable CSVs, catalogue/version metadata, corrections,
feedback, and optionally selected originals, sanitized reports, and intake media. The export warns
that it may contain sensitive data before opening the system share sheet.

Restoring an export and password-encrypting the archive are post-MVP unless the protected schedule
finishes early. Ordinary export, local deletion, cloud account export, and cloud account deletion
remain launch requirements.

Deletion is implemented as a domain operation that removes dependent database rows and referenced
files transactionally as far as the platform permits, then verifies no orphaned app-controlled file
remains.

## Failure model

Every durable workflow ends in an observable state:

- import: draft, needs review, confirmed, failed, or deleted;
- cloud job: queued locally, uploading, submitted, processing, ready, applied, failed, expired, or
  cancelled before submission;
- catalogue update: installed, rejected with current version retained, or unavailable; and
- purchase: pending, active, exhausted, expired, revoked, or restored.

Failures preserve the Original Report, Intake Event, user corrections, and local queue. Retry never
duplicates a report, event, charge, or allowance transaction.

## Verification architecture

Use synthetic and explicitly de-identified fixtures only.

Verification is risk-based, with no coverage-percentage target. Automate the non-trivial boundaries
where failure can corrupt data, privacy, billing, health wording, parsing, or asynchronous recovery;
use typechecking and focused integrated checks for obvious low-risk wiring and static presentation.

- TypeScript domain and contract tests run without a simulator.
- Repository tests use temporary SQLite databases and exercise every migration from version zero.
- Swift XCTest covers OCR/PDF transforms, password handling, metadata removal, redaction flattening,
  file protection, and cloud-envelope test vectors.
- Contract tests run the same JSON fixtures through mobile and backend decoders.
- Backend integration tests use temporary SQLite databases and upload directories plus fake
  providers, clocks, process restarts, and RevenueCat webhook events to prove leasing, deployment
  recovery, idempotency, cleanup, expiry, and charging rules.
- A deterministic showcase mode seeds the real production screens for App Store screenshots.
- The protected release flow is exercised on an iPhone 15 Pro running iOS 26 and a current iOS 26
  iPhone, in light/dark mode, large Dynamic Type, VoiceOver spot checks, and offline/poor-network
  states.

## Explicit non-goals

The first architecture does not include HealthKit, iCloud health sync/backup, Android behavior,
BYOK, arbitrary provider URLs, multi-person profiles, clinician sharing, notification infrastructure,
medication reasoning, an agent SDK in the client, or a server-side health-record database.
